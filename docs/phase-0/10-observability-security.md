# Phase 0 — Observability & Security Design

## Part A: Observability Design

### 1. The Three Pillars

| Pillar | What It Tells You | Tool |
|--------|-------------------|------|
| **Logs** | What happened | Pino (structured JSON) |
| **Metrics** | How much / how often | In-memory counters exposed via `/admin/metrics` |
| **Traces** | Where the request traveled | Correlation IDs propagated across services |

### 2. Structured Logging

All logs are JSON objects via Pino. This enables machine parsing, filtering, and aggregation.

#### Log Fields

| Field | Source | Description |
|-------|--------|-------------|
| `level` | Pino | `info`, `warn`, `error`, `debug` |
| `timestamp` | Pino | ISO-8601 |
| `service` | Config | `user-service` or `order-service` |
| `requestId` | Middleware | UUID, unique per HTTP request |
| `correlationId` | Middleware | UUID, shared across service calls for the same client request |
| `method` | Middleware | HTTP method |
| `path` | Middleware | Request path |
| `statusCode` | Middleware | Response status code |
| `durationMs` | Middleware | Request processing time |
| `msg` | Application | Human-readable message |
| `error` | Application | Error details (if applicable) |
| `userId` | Application | Relevant user ID (if applicable) |
| `orderId` | Application | Relevant order ID (if applicable) |
| `eventId` | Application | Relevant event ID (if applicable) |

### 3. Request ID and Correlation ID

| Concept | Scope | Purpose |
|---------|-------|---------|
| **Request ID** | Single service | Identifies one HTTP request within one service. Generated by each service if not present in headers. |
| **Correlation ID** | Cross-service | Identifies the entire request chain initiated by the client. Propagated from Order Service to User Service. Included in RabbitMQ messages. |

**Flow:**
```
Client → Order Service (generates correlationId if absent)
  → User Service HTTP call (X-Correlation-ID header)
  → Outbox event (correlationId field)
  → RabbitMQ message (correlationId field)
  → User Service consumer (reads correlationId, logs with it)
```

### 4. Health Endpoint

**Path:** `GET /health`

**Purpose:** Liveness check. Answers: "Is the process running?"

**Checks:** None (just returns 200). If the HTTP server can respond, the process is alive.

**Usage:** Docker `HEALTHCHECK`, monitoring systems.

### 5. Readiness Endpoint

**Path:** `GET /ready`

**Purpose:** Readiness check. Answers: "Can this service handle requests?"

**Checks:**
- Database connection (execute `SELECT 1`)
- RabbitMQ connection (check channel is open)

**Usage:** Load balancers, Docker Compose `depends_on` with `condition: service_healthy`.

## Part B: Security Design

### 1. Service-to-Service Authentication

| Aspect | Design |
|--------|--------|
| Mechanism | Shared secret (pre-shared key) via `X-Service-Auth` header |
| Secret source | Environment variable `SERVICE_AUTH_TOKEN` |
| Scope | Order Service → User Service internal endpoints only |
| Validation | Constant-time string comparison to prevent timing attacks |

**Why a shared secret and not JWT/OAuth:**
- This is an assignment, not a production SaaS. A shared secret clearly demonstrates the concept of service-to-service authentication.
- JWT would require a token issuer, key management, and token refresh — unnecessary complexity.
- The shared secret is stored in environment variables, not hard-coded.

### 2. Admin/Control Plane Authentication

| Aspect | Design |
|--------|--------|
| Mechanism | API key via `X-Admin-Key` header |
| Secret source | Environment variable `ADMIN_API_KEY` |
| Scope | All `/admin/*` endpoints on both services |
| Validation | Constant-time string comparison |

### 3. Secret Management

| Secret | Storage | Never In |
|--------|---------|----------|
| `SERVICE_AUTH_TOKEN` | `.env` file (gitignored), Docker Compose env | Source code, git history |
| `ADMIN_API_KEY` | `.env` file (gitignored), Docker Compose env | Source code, git history |
| Database passwords | `.env` file (gitignored), Docker Compose env | Source code, git history |
| RabbitMQ credentials | `.env` file (gitignored), Docker Compose env | Source code, git history |

An `.env.example` file with placeholder values is committed to the repository.

### 4. Input Validation

| Layer | Tool | Purpose |
|-------|------|---------|
| Request body | Zod schemas | Type validation, format validation, constraints |
| Path parameters | Zod + middleware | UUID format validation |
| Query parameters | Zod | Pagination bounds, enum values |
| Headers | Custom middleware | Required headers (Idempotency-Key, auth headers) |

All validation errors return `400 VALIDATION_ERROR` with details about which fields failed.

### 5. Rate Limiting

| Endpoint | Limit | Window | Rationale |
|----------|-------|--------|-----------|
| `POST /users` | 10 req/min/IP | 1 minute | Prevent spam user creation |
| `POST /orders` | 20 req/min/IP | 1 minute | Prevent spam order creation |
| `/admin/*` | 30 req/min/IP | 1 minute | Prevent brute-force of admin key |

**Implementation:** In-memory rate limiter (express-rate-limit). No Redis needed for single-instance deployment.

**Design choice:** Rate limits are intentionally generous for a demo/testing environment. In production, they would be stricter.

### 6. CORS

| Setting | Value |
|---------|-------|
| `origin` | `http://localhost:3002` (Reliability Console) |
| `methods` | `GET, POST` |
| `allowedHeaders` | `Content-Type, X-Request-ID, X-Correlation-ID, Idempotency-Key, X-Admin-Key, X-Service-Auth` |
| `credentials` | `false` |

### 7. Secure Headers

Using `helmet` middleware for Express:

| Header | Value |
|--------|-------|
| `X-Content-Type-Options` | `nosniff` |
| `X-Frame-Options` | `DENY` |
| `X-XSS-Protection` | `0` (deprecated, modern browsers don't need it) |
| `Strict-Transport-Security` | Not set (HTTP only in development) |
| `Content-Security-Policy` | Default restrictive policy |

### 8. Request Size Limits

| Limit | Value | Rationale |
|-------|-------|-----------|
| JSON body | `1MB` | Orders with 50 items won't exceed this; prevents memory exhaustion |
| URL length | `2048 chars` | Standard browser limit |

### 9. Authorization Model

| Caller | Can Access |
|--------|-----------|
| Any client | Public endpoints: `POST /users`, `GET /users/:id`, `POST /orders`, `GET /orders/:id`, `/health`, `/ready` |
| Order Service (with `X-Service-Auth`) | Internal endpoints: `GET /internal/users/:id/verify` |
| Admin (with `X-Admin-Key`) | Admin endpoints: `/admin/*` |

This is a simple three-tier model. No user-level authentication/authorization is implemented (clients are anonymous). This is appropriate for an assignment that focuses on distributed-systems concerns rather than user auth.
