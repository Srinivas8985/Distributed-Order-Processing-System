# Phase 0 — Idempotency Design

## 1. Overview

Idempotency ensures that if a client sends the same `POST /orders` request multiple times (due to network retry, timeout, or client-side retry), the order is created exactly once and subsequent requests receive the original response.

## 2. Mechanism

### 2.1 The Idempotency-Key Header

```
Idempotency-Key: abc123-unique-client-key
```

- **Generated by:** The client (Postman, frontend, etc.)
- **Scope:** `POST /orders` endpoint only (GET requests are naturally idempotent)
- **Format:** Any string, 1–255 characters. Recommended: UUID v4.
- **Required:** Yes. Requests without this header receive `400 VALIDATION_ERROR`.
- **Lifetime:** 24 hours from creation. After expiry, the key can be reused.

### 2.2 Request Hash

A SHA-256 hash of the canonical request body is computed and stored alongside the idempotency key.

**Purpose:** Detect when a client reuses the same `Idempotency-Key` with a different request body (which is a client error, not a legitimate retry).

**Canonical form:** `JSON.stringify()` of the validated, trimmed request body with keys sorted. This ensures whitespace and key-order differences don't produce false hash mismatches.

## 3. Processing Flow

### 3.1 First Request

```
1. Extract Idempotency-Key from header
2. Compute request_hash = SHA-256(canonical body)
3. BEGIN TRANSACTION
4. INSERT INTO idempotency_keys (key, request_hash, response_code, response_body)
   → If UNIQUE violation: this is a concurrent duplicate (see 3.3)
5. Verify user via User Service
6. INSERT INTO orders
7. INSERT INTO order_items  
8. INSERT INTO outbox_events
9. UPDATE idempotency_keys SET response_code = 201, response_body = {order}
10. COMMIT
11. Return 201 Created
```

### 3.2 Repeated Request (Same Key, Same Body)

```
1. Extract Idempotency-Key from header
2. Compute request_hash
3. SELECT FROM idempotency_keys WHERE key = ?
   → Found, and request_hash matches
4. Return the stored response_code and response_body
   → 200 OK (not 201, to signal this is a replay)
```

### 3.3 Concurrent Duplicate Requests

This is the critical case that justifies database-level enforcement.

```
Request A: INSERT INTO idempotency_keys → succeeds (row locked by transaction)
Request B: INSERT INTO idempotency_keys → UNIQUE constraint violation

Request B catches the violation:
  → Waits briefly (100ms)
  → Re-reads idempotency_keys WHERE key = ?
  → If found with response_body populated: return cached response
  → If found but response_body is NULL (Request A still in-flight):
    → Return 409 Conflict with message "Request in progress"
```

### 3.4 Same Key, Different Body

```
1. Extract Idempotency-Key
2. Compute request_hash
3. SELECT FROM idempotency_keys WHERE key = ?
   → Found, but request_hash does NOT match
4. Return 409 IDEMPOTENCY_CONFLICT
   "This Idempotency-Key was already used with a different request body"
```

## 4. Why Application-Level "Check Then Insert" Fails

A naive implementation:

```typescript
// WRONG — race condition
const existing = await db.idempotencyKey.findUnique({ where: { key } });
if (existing) {
  return existing.response;
}
await db.idempotencyKey.create({ data: { key, ... } });
```

**The problem:**

```
Time    Request A                    Request B
────────────────────────────────────────────────
t1      SELECT → not found
t2                                   SELECT → not found
t3      INSERT → success
t4                                   INSERT → success (DUPLICATE!)
t5      Create order...
t6                                   Create order... (DUPLICATE ORDER!)
```

Both requests pass the check, both insert, and two orders are created.

**The solution:** Use the database `UNIQUE` constraint on `idempotency_keys.key`. The second `INSERT` fails with a unique-constraint violation, which the application catches and handles. The database serializes concurrent access correctly.

**Alternative approach (also valid):** Use `INSERT ... ON CONFLICT DO NOTHING` and check the affected row count. If 0 rows inserted, the key already exists.

## 5. Lifecycle and Retention

| Phase | Duration | Action |
|-------|----------|--------|
| Active | 0–24 hours | Key is live; duplicates return cached response |
| Expired | After 24 hours | Key eligible for cleanup |
| Cleanup | Background job (hourly or daily) | `DELETE FROM idempotency_keys WHERE expires_at < NOW()` |

**Why 24 hours:**
- Long enough to handle realistic retry scenarios (network issues, client restarts)
- Short enough to prevent unbounded table growth
- Configurable via environment variable `IDEMPOTENCY_KEY_TTL_HOURS`

## 6. Edge Cases

| Scenario | Behavior |
|----------|----------|
| Key present, original request returned 400 | Return cached 400 (client should fix the request and use a new key) |
| Key present, original request returned 503 | Return cached 503 (client should retry with a NEW key, because the order was never created) |
| Key present, original request succeeded (201) | Return 200 with cached order |
| Key expired and reused | Treated as a new request (new order created) |
| Request without Idempotency-Key | 400 VALIDATION_ERROR |
| Idempotency-Key with empty string | 400 VALIDATION_ERROR |

**Design decision — caching error responses:**

We cache responses for ALL completed requests, including errors. This prevents a scenario where:
1. Request A arrives, user verification fails → 503
2. Idempotency key is not stored
3. Request B arrives with same key, user is now available → 201
4. Request A's client retries → gets 201 (different response for "same" request)

By caching the 503, Request A's retry gets the same 503, and the client knows to use a new key.

**Exception:** If the transaction itself fails (database error during COMMIT), the idempotency record is rolled back along with everything else. The client can safely retry with the same key.

## 7. Interaction with Other Patterns

### Idempotency + Outbox
The idempotency record is created in the same transaction as the order and outbox event. All three succeed or fail atomically.

### Idempotency + Retries
When Order Service retries a call to User Service, the retry is a new HTTP request to a different service — it has nothing to do with the `Idempotency-Key` (which is about the client→Order Service boundary). The client's key remains valid regardless of how many internal retries occur.

### Idempotency + Circuit Breaker
If the circuit breaker is open, Order Service returns 503 immediately. The idempotency key is NOT consumed (the transaction never starts), so the client can retry with the same key later.
